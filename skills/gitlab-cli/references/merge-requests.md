# Merge Request Operations

## List MRs

```bash
glab mr list                              # Open MRs (default)
glab mr list --all                        # All MRs
glab mr list --assignee=@me               # Assigned to me
glab mr list --reviewer=@me               # I'm reviewer
glab mr list --author=username            # By author
glab mr list --source-branch=feature      # By source branch
glab mr list --target-branch=main         # By target branch
glab mr list --label=bugfix               # By label
glab mr list --draft                      # Draft MRs only
glab mr list --merged                     # Merged MRs
glab mr list --closed                     # Closed MRs
glab mr list --search "feature X"         # Search title/description
glab mr list -F json                      # JSON output
```

Combine flags: `glab mr list --assignee=@me --label=urgent --target-branch=main`

## Create MR

```bash
# Interactive
glab mr create

# Preferred: explicit title + explicit description (avoid accidental autofill noise)
glab mr create -t "PROJ-123: Title" -d "Description" --remove-source-branch

# Preferred with assignees/reviewers/target branch
glab mr create \
  -t "PROJ-123: Title" \
  -d "Description" \
  -a user1,user2 \
  --reviewer reviewer1,reviewer2 \
  -b main \
  --remove-source-branch \
  --yes

# If using --fill, ALWAYS run a post-create description sanity check and clean up if needed
glab mr create -f --yes
```

Flags: `-t`/`--title`, `-d`/`--description` (NOT `--body`), `-a` assignee, `-l`
labels, `-m` milestone, `-b` target branch, `--draft`, `--reviewer`, `--push`,
`--remove-source-branch`.

Prefer explicit `--title` + `--description`. Use `-f/--fill` only when asked,
and always verify/clean the MR description afterward.

### MR Description Template (Required for Create)

Fill every field with concrete sentences (not placeholders), then run
`glab mr create` with the completed description.

```markdown
## Summary

<!-- What this MR does and why. Lead with the verb and the affected component. -->

## Impact

<!-- Blast radius: which systems/customers/workflows are affected, how severely. "None" only if true. -->

## Regression Coverage

<!-- Which existing tests cover this, or what new tests were added. If absent, say so. -->

## Post-Deploy Checklist

<!-- The one thing to verify after deploy, and how to roll back (command, est. time). -->

## Soak Period

Standard - default soak time.

## Dependencies

<!-- Version pins, feature flags, config, or sibling deploys needed first. "None" if none. -->
```

### MR Description Hygiene (Required)

After creating/updating an MR, always verify the body before reporting success:

```bash
glab mr view <MR_ID> -F json | jq -r '.description'
```

If description contains unexpected generated content (for example,
`<!-- CURSOR_SUMMARY -->`, bot signatures, or unrelated templates), overwrite
immediately:

```bash
glab mr update <MR_ID> --description "$CLEAN_DESCRIPTION" --yes
```

Never leave noisy/autogenerated sections in the final MR unless the user
explicitly asks for them.

### Safe MR Workflow (Required for agents)

1. Create branch, commit, and push.
2. Create MR with explicit `--title` and `--description` (include Jira prefix
   when required).
3. Set `--remove-source-branch`.
4. Verify MR with `glab mr view <MR_ID> -F json` and check
   title/description/assignees.
5. If anything is off, fix with `glab mr update` before sharing the MR link.

### Common Pitfalls (gh vs glab)

| glab (GitLab)          | gh (GitHub)          | Notes                                                                     |
| ---------------------- | -------------------- | ------------------------------------------------------------------------- |
| `-d`/`--description`   | `--body`             | MR/PR description text                                                    |
| `-b`/`--target-branch` | `--base`             | Target branch for merge                                                   |
| `-a`                   | `--assignee`         | Same meaning, different syntax                                            |
| `-l`                   | `--label`            | Same meaning, different syntax                                            |
| `-F/-O` output flags   | often `-o` elsewhere | `glab` output flags are command-specific (`mr`: `-F`, `issue list`: `-O`) |

## View MR

```bash
glab mr view 123                          # View MR details
glab mr view 123 -c                       # Include comments
glab mr view 123 -w                       # Open in browser
glab mr view 123 -F json                  # JSON output
glab mr view feature-branch               # View by branch name
```

## Merge MR

```bash
glab mr merge 123                         # Merge MR
glab mr merge 123 -y                      # Skip confirmation
glab mr merge 123 -s                      # Squash commits
glab mr merge 123 -d                      # Delete source branch
glab mr merge 123 -r                      # Rebase before merge
glab mr merge 123 -m "Custom message"     # Custom merge commit message
glab mr merge                             # Merge MR for current branch
```

## Other MR Operations

```bash
glab mr checkout 123                      # Checkout MR branch
glab mr checkout 123 -b local-branch      # Checkout with custom branch name
glab mr approve 123                       # Approve MR
glab mr revoke 123                        # Revoke approval
glab mr close 123                         # Close MR
glab mr reopen 123                        # Reopen MR
glab mr update 123 -t "New title"         # Update MR
glab mr note 123 -m "Comment"             # Add comment
glab mr diff 123                          # View diff
glab mr rebase 123                        # Rebase MR
glab mr todo 123                          # Add to todo list
```
